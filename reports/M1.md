> 日期：2026-11-14 ｜ 状态：**完成** ｜ 通过项：T2

---

## 1. 结论

fork 出来的推理引擎已接入项目，`RolloutEngine.generate_batch()` 能稳定返回
**token ids + 每 token logprob**，与训练侧 SDPA forward 的误差远低于门槛，
真实模型的轨迹现在可以实时推到浏览器里看。

过程中发现并修掉了 3 个会直接毁掉训练的问题：

1. 引擎 `_step` 没有 `no_grad` → 每批泄漏 **~3GB** 显存，4GB 卡三轮必 OOM；
2. prefill 计算全序列 logits → **(B,S,V) 622MB**，现降到 (B,1,V) 2.4MB；
3. 只认 `<|im_end|>`，漏掉 `<|endoftext|>` → 请求会空转到 `max_tokens`。

另外测出一个**比代码更重要的结论**：Qwen3-0.6B 目前基本无法把观测接地
（能调工具，但读不懂坐标/网格），SFT 冷启动从"可选"变成"必须"。

## 3. 引擎改动

### 3.1 功能改动（4 改 1 增）

| 文件 | 改动 |
|---|---|
| `server.py` `sample_one()` | 返回 `(token, logprob)`，logprob 取**采样变换之前**的原始分布 |
| `server.py` `Engine._step()` | 逐请求收集 logprob，完成时写入 `job.logprobs` |
| `server.py` 响应 | chat / completion 都新增 `token_ids` / `logprobs` |
| `qwen3/request.py` | `append(token, logprob)` + `output_logprobs` |
| `qwen3/scheduler.py` | `on_step_done(batch, tokens, logprobs)` |
| `engine_rl.py` | 新增，进程内批量接口 |

### 3.2 Bug 修复

**① `no_grad` 缺失（最严重）**

上游 `Engine._step()` 没包 `torch.no_grad()`。推理不 backward，但 PyTorch 仍为
每次前向建反图，28 层激活全部常驻。

实测（8 路 × 256 token prefill，RTX 3050 4GB）：

| 阶段 | 修复前 | 修复后 |
|---|---|---|
| 加载 + KV 池 | 2106 MiB | 2106 MiB |
| round 0 | 5246 MiB | 2114 MiB |
| round 1 | 8338 MiB | 2114 MiB |
| round 2 | 10831 MiB | 2114 MiB |
| round 3 | **OOM** | 2115 MiB |

每轮泄漏 ~3GB。上游 HTTP 服务同样受影响，只是单请求泄漏慢、不容易被发现。

**② prefill 全序列 logits**

`Qwen3ForCausalLM.forward()` 新增 `last_positions`：只对每个请求的最后一个位置
做 `lm_head`。S=256 / V=151936 / bf16 时 **622MB → 2.4MB**。

**③ 多 EOS**

`generation_config.json` 的 `eos_token_id` 是 `[151645, 151643]`，上游只认前者。
漏掉 `<|endoftext|>` 会让请求跑满 `max_tokens`，垃圾 token 直接进 loss。

## 4. T2 校准结果

**PASS**

| 指标 | 实测 | 门槛 |
|---|---|---|
| tokens | 19 | — |
| `max｜Δ｜` | **0.000417** | < 1e-2 |
| `mean｜Δ｜` | **0.000057** | < 1e-3 |
| `ratio` 范围 | **[0.999583, 1.000204]** | [0.98, 1.02] |

（首版用的是手写 prompt，max 0.0080 贴着门槛；换成和真实 rollout
完全一致的 `prompts.render_prompt` 后降到 0.0004。）

对比的两条路径就是实际使用的那两条：

- **A（引擎）**：Triton varlen flash prefill + KV cache + eager decode
- **B（训练）**：`QWEN3_FLASH_ATTN=pytorch` → SDPA，整条序列一次前向

第 0 步 ratio 可以把偏差压到 1% 以内，GRPO 的 clip 完全能吃下。

> 误差来源是 bf16 下两条 kernel 的归约顺序不同。若后续 prompt 拉长到
> >1000 token 后误差变大，应把两侧的 `log_softmax` 都保持 fp32
> （当前引擎侧已是 `.float()`，训练侧也是）。

## 5. 性能与显存实测

| 场景 | 耗时 |
|---|---|
| 单请求，19 token 输出（含 244 token prefill） | **0.94 s** |
| 8 路并发，19 token 输出 | **1.2 – 1.7 s** |
| 30 步 episode（单轨迹，串行） | **~29 s** |
| KV 池 | 384 块 × 16 = 6144 token，672 MB |
| 常驻显存（模型+池） | **2114 MiB**，6 轮 rollout 后不变 |

推算：G=8、30 轮的一组 rollout 约 **40–60 s**；200 次更新约 **4 小时**。
比计划的 7 小时好，主要得益于 `last_positions` 和批处理。

## 6. 真实模型基线（重要）

用 `EnginePolicy` 跑真模型（Qwen3-0.6B-Instruct，greedy）：

| 场景 | 结果 |
|---|---|
| L0（空地）30 步 | 0/2 成功，29 次撞墙 |
| L3（U 型墙）30 步 | 0/2 成功，28 次撞墙 |
| 工具调用格式 | **100% 合法** |
| 平均延迟 | 946 ms / 步 |

典型轨迹：模型连续 30 次输出 `direction: "right"`，哪怕 `delta=(-4,-1)`。

**接地小实验**（12×12 空地 + 显式坐标，8 组随机起终点）：

| 观测变体 | 合法输出 | 选择能缩短距离的动作 |
|---|---|---|
| 网格 + 坐标 | 4/8 | 4/8 |
| 网格 + 坐标 + `delta=(dx,dy)` | **8/8** | **7/8** |
| 仅 delta | 8/8 | 7/8 |
| delta + 明文解释 | 8/8 | 7/8 |

结论：

- **格式没问题**（工具调用模板学得很好），问题在**空间接地**；
- 加上显式 `delta` 后合法率从 50% → 100%，所以 `render.py` 已改为
  `pos=… goal=… delta=(+6,+2)`，并在表头标注 `x=right y=down`；
- 但在**带墙**的地图上仍然基本失效（三轮 case 里只有 0–1 次选对）。
  12×12 的 144 个 `.` 会稀释模型对坐标的注意力；局部视野在单点测试里
  看起来更好，但样本太小，**结论留到 SFT 之后再测**。

**行动项**：M2 的 SFT 冷启动从"建议"升级为"必须"。SFT 目标不是教格式，
而是教"读坐标 + delta 选方向"这件最基本的接地能力。

## 7. 采样多样性（给 M3 的参数）

8 路采样，同一 prompt，统计方向 token 的分布：

| 温度 | 不同动作数 | 合法率 |
|---|---|---|
| 0.7 | 3 | 8/8 |
| 0.9 | 1 | 8/8 |
| 1.0 | 1 | 8/8 |
| 1.1 | 2 | 8/8 |
| 1.2 | 4 | 8/8 |

小样本噪声大，但可以确定：**温度 1.0–1.2 不会破坏 JSON 格式**（之前的
非法输出是 OOM 导致的，不是温度）。M3 先用 `T=1.0`，组内退化再升到 1.2。

> 注意：`Sampling.temperature` 只影响采样；记录进 `old_logps` 的永远是
> 原始分布的 logprob，所以训练侧不需要做温度补偿。

## 8. 已知限制

| 项 | 说明 |
|---|---|
| CUDA Graph | `runner=None`，decode 走 eager。正确性优先，M3 再开 |
| 权重加载峰值 | GPU 上会多复制一份 state_dict（~1.2GB 瞬时），随后回落 |
| 单请求延迟 | ~0.9s/步，30 步 episode 需要 29s；只能靠批处理摊薄 |
| 模型接地 | 带墙地图上基本不可用，必须 SFT |
| 引擎单测 | fork 自带测试需要 torch，已从 pytest 收集范围排除 |
